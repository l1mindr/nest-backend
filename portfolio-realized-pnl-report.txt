PORTFOLIO REALIZED P&L REPORT — MILESTONE M6.2
=============================================

1. OBJECTIVE
============

Extend the portfolio calculation domain (M6.1) with realized P&L and the
cost-basis policies that produce it:

  - SELL and TRANSFER_OUT now release cost basis instead of reducing quantity
    only.
  - Every SELL produces a realized P&L event (price, proceeds, released basis,
    signed gain/loss).
  - Three cost-basis strategies are implemented behind the existing
    CostBasisCalculator interface: AVERAGE, FIFO and LIFO.
  - The engine accepts a strategy by enum or an injected calculator instance.

As in M6.1, everything lives in the pure domain layer:

  src/features/portfolio/domain/calculation/

No migrations, no controllers, no DTOs, no Swagger, no application-layer
wiring, and no holdings mutation. Results are computed on demand and never
persisted.

2. M6.1 BASELINE
================

M6.1 (portfolio-calculation-engine-report.txt) delivered the pure
PortfolioCalculationEngine and the AVERAGE cost-basis calculator. At that
point SELL only reduced `quantity`; `totalCost` was left untouched, and the
transfer-out basis policy and realized P&L were explicitly deferred. M6.2
resolves both. The M6.1 engine surface is preserved: `calculate(input)` still
returns `{ quantity, totalCost, averageCost }`, now extended with
`realizedPnl`.

3. COST-BASIS POLICY
====================

Three strategies implement the same CostBasisCalculator interface:

  - AVERAGE: all acquisition cost is pooled; a disposal releases a
    proportional share `amount × (totalCost / quantityBefore)`.
  - FIFO: each acquisition creates a lot; a disposal consumes the oldest
    lots first and releases their exact cost.
  - LIFO: lot-based; a disposal consumes the newest lots first.

Invariants shared by all three:

  - A disposal can never release more cost basis than the strategy currently
    holds (availability is checked before any release computation).
  - Quantity can never go negative.
  - Remaining cost basis after a disposal is `previousCostBasis − released`.
  - TRANSFER_IN never creates acquisition cost (zero basis).
  - Only SELL realizes P&L; TRANSFER_OUT is a custody move.

Strategy selection (§4) is the only surface the engine exposes; the policies
themselves are interchangeable and unit-tested independently.

4. STRATEGY SELECTION
=====================

  PortfolioCalculationEngine(costBasis: CostBasisCalculator | CostBasisStrategy)

  - Default: CostBasisStrategy.AVERAGE (backward compatible — the old no-arg
    and injected-calculator constructions behave exactly as before).
  - Enum values AVERAGE | FIFO | LIFO map to module-level stateless calculator
    singletons; an injected calculator instance is used directly.
  - The same ledger discriminates the policies:
      buy 1 @ 100, buy 1 @ 200, sell 1 @ 150 →
        AVERAGE: released 150, gain 0,   remaining cost 150
        FIFO:    released 100, gain 50,  remaining cost 200
        LIFO:    released 200, gain -50, remaining cost 100

5. AVERAGE COST IMPLEMENTATION
==============================

  AverageCostCalculator implements CostBasisCalculator.

  BUY:          quantity += amount; totalCost += amount × price.
  SELL:         releasedBasis = amount × (totalCost / quantityBefore);
                totalCost -= releasedBasis; realized P&L event recorded.
  TRANSFER_IN:  quantity += amount; never creates acquisition cost.
  TRANSFER_OUT: releases basis exactly like SELL but records NO event.

  The average cost of the remainder is unchanged by a sale (mathematically
  exact except when the per-sale average is a non-terminating quotient, which
  is truncated at CALCULATION_DIVISION_MAX_FRACTION_DIGITS — see §10).

6. FIFO IMPLEMENTATION
======================

  FifoCostBasisCalculator extends LotCostBasisCalculator with fromBack=false.

  BUY          pushes a lot { amount, price } — per-unit cost is the exact
               BUY price.
  SELL         consumes lots from the front (oldest first); releasedBasis is
               the exact sum of consumed × unitCost; event recorded.
  TRANSFER_IN  pushes a zero-cost lot { amount, 0 }.
  TRANSFER_OUT consumes lots from the front identically but records NO event.

  Opening position is a single lot whose per-unit cost is
  openingCost / openingQuantity (see §3 / §11). Exhausted lots are dropped;
  remaining lots keep acquisition order.

7. LIFO IMPLEMENTATION
======================

  LifoCostBasisCalculator extends LotCostBasisCalculator with fromBack=true.

  Identical to FIFO except that disposals consume lots from the back (newest
  first). Shared behavior lives in LotCostBasisCalculator and in the pure
  consumeLots(lots, amount, fromBack) helper in lot.ts, which never mutates
  its input and returns a fresh remainder plus the released basis.

8. TRANSFER_IN ZERO-BASIS POLICY
================================

  TRANSFER_IN adds units without creating acquisition cost. The strategy
  tracks the units so they can later be sold or transferred out:

    - AVERAGE: quantity += amount; totalCost unchanged (a transfer price is
      preserved but never interpreted as acquisition cost).
    - FIFO/LIFO: pushes a zero-cost lot { amount, unitCost: '0' }.

  Consequence: selling zero-basis units realizes a gain equal to the full
  proceeds (releasedBasis = 0). Multiple zero-cost transfer lots behave like
  any other lots under FIFO/LIFO ordering.

9. TRANSFER_OUT SEMANTICS
=========================

  TRANSFER_OUT releases cost basis exactly like SELL but produces NO realized
  P&L event. A custody move out of the portfolio is not a disposal: it removes
  units (and their basis) from the position without realizing a gain. This
  keeps the remainder's basis correct and lets FIFO/LIFO consume the correct
  lots.

  A TRANSFER_OUT must never use its optional price to generate proceeds or
  P&L. In the result, a transfer-out is therefore visible only through the
  reduced quantity/totalCost and the absence of an event for it — an
  equivalent representation of "proceeds = 0, realized P&L = 0".

10. REALIZED P&L FORMULA
========================

  Per SELL disposal the event carries:

  { transactionId?, occurredAt, type: 'SELL', amount, price, proceeds,
    releasedCostBasis, realizedPnl, fee? }

    proceeds          = amount × price            (exact)
    releasedCostBasis = policy-specific (see above)
    realizedPnl       = proceeds − releasedCostBasis   (signed decimal)

  - Events appear in chronological processing order; empty when no SELL.
  - P&L is reported GROSS of fees: `proceeds` is `amount × price`, the
    transaction fee is carried on the event (`fee`), and the application
    layer decides how to net it. Fees are still never merged into `totalCost`.

11. DECIMAL PRECISION BEHAVIOR
==============================

  All arithmetic remains BigInt-based and exact where a finite decimal exists.
  Two unavoidable truncation points are documented and tested:

  - Average-cost per-sale release when totalCost / quantityBefore does not
    terminate: buy 1 @ 1, buy 2 @ 0.5, sell 1 @ 1 →
      released 0.66666666666666666666666666, gain 0.33333333333333333333333334
      (truncated toward zero at 26 fractional digits).
  - Opening-lot per-unit cost for FIFO/LIFO, same cap.

  BUY lots are always exact (released basis = sold × exact price), so a ledger
  with no opening position has zero approximation error under FIFO/LIFO.

12. DOMAIN ARCHITECTURE
=======================

  All M6.2 code sits in the pure domain layer:

    portfolio/domain/calculation/
    ├── cost-basis.calculator.ts        CostBasisCalculator interface
    ├── cost-basis-validation.ts        shared validation (split out in M6.2)
    ├── average-cost.calculator.ts      AVERAGE policy
    ├── lot.ts                          Lot model + consumeLots pure helper
    ├── lot-cost-basis.calculator.ts    shared lot accounting + FIFO/LIFO
    ├── portfolio-calculation.engine.ts chronology + strategy selection
    └── types/
        ├── cost-basis.strategy.enum.ts AVERAGE | FIFO | LIFO
        ├── calculation-result.types.ts RealizedPnlEvent + realizedPnl
        ├── calculation-input.types.ts  (M6.1)
        └── calculation-transaction.types.ts (M6.1)

  The engine sorts by occurredAt (id tie-breaker, stable fallback) and
  delegates to the selected strategy. Strategies are stateless and return new
  result objects; inputs are never mutated. No Nest, TypeORM, or express
  imports anywhere in this subtree.

13. ERROR HANDLING
==================

  Reuses the M6.1 validation vocabulary unchanged. No new error codes were
  needed; all three strategies share the extracted cost-basis-validation
  module:

  - Disposals exceeding the held quantity fail deterministically with
    INSUFFICIENT_QUANTITY before any basis is released (the availability
    check always precedes the release computation, so division by a zero
    quantity cannot occur).
  - Malformed/negative amounts, prices and fees, missing price on BUY/SELL,
    unsupported transaction types, and invalid opening state behave exactly
    as in M6.1.
  - Errors are thrown as CalculationError with a stable CalculationErrorCode;
    they are not swallowed anywhere.

14. INPUT / OUTPUT TYPES
========================

  Input  (M6.1, unchanged):
    PortfolioCalculationInput {
      assetId?: string;
      openingQuantity?: string;   // default '0'
      openingCost?: string;       // default '0'
      transactions: CalculationTransaction[];
    }
    CalculationTransaction {
      id?: string; occurredAt: string; type: BUY | SELL | TRANSFER_IN |
      TRANSFER_OUT; amount: string; price?: string; fee?: string;
    }

  Output  (M6.1 surface extended):
    PortfolioCalculationResult {
      quantity: string;          // exact decimal
      totalCost: string;         // exact decimal (remaining basis)
      averageCost: string;       // '0' when quantity is zero
      realizedPnl: RealizedPnlEvent[];
    }

  All monetary values are exact decimal strings. No JavaScript numbers are
  involved in computation.

19. EXPLICITLY DEFERRED WORK (M6.3+)
====================================

  - Unrealized P&L and current value (M6.3): the engine input gains a
    `currentPrice` supplied by the application layer; currentValue =
    quantity × currentPrice, unrealized = currentValue − remaining basis.
  - Fee accounting: realized P&L is gross of fees; the exact netting policy
    (buy fees into basis, sell fees against proceeds) is an application-layer
    decision and is deferred.
  - API surface: no GET /v1/portfolios/:portfolioId/pnl; CalculationError
    codes are still not mapped to HTTP errors.
  - Persistence: nothing is stored; no cached P&L columns.
  - Application-layer wiring: registering the engine (and a chosen default
    strategy) through Nest DI, and mapping domain inputs/outputs to repository
    data.

20. ARCHITECTURAL CONSIDERATIONS
================================

  - The AVERAGE strategy's disposal release reuses the same
    CALCULATION_DIVISION_MAX_FRACTION_DIGITS cap as averageCost, so per-sale
    basis and the reported average are consistent by construction. If the
    product ever needs a bounded presentation scale, that remains a
    presentation decision.
  - TRANSFER_OUT releasing basis is a behavior change from M6.1 (which kept
    totalCost untouched) and is intentional: releasing basis on a custody
    move is required to keep the remainder's basis correct. The M6.1 tests
    that asserted the old behavior were updated as part of the feature
    commit.
  - The realized P&L event is SELL-only by design (transfers produce no P&L),
    which keeps the disposal list a faithful audit trail of realized gains.
  - No new dependencies, patterns, or abstractions were introduced; the
    strategies compose behind the existing M6.1 interface.

21. EXAMPLE CALCULATIONS
========================

  Ledger: BUY 1 @ 50000, BUY 2 @ 70000, SELL 1.5 @ 80000.

  AVERAGE:
    totalCost = 50000 + 140000 = 190000; quantity = 3; average = 63333.33...
    released  = 1.5 × (190000 / 3) = 95000
    proceeds  = 1.5 × 80000 = 120000
    realizedPnl = 120000 − 95000 = 25000
    remainder = { quantity 1.5, totalCost 95000 } (average unchanged)

  FIFO:
    lots = [1 @ 50000, 2 @ 70000]
    consume 1 @ 50000 + 0.5 @ 70000
    released  = 50000 + 35000 = 85000
    proceeds  = 120000; realizedPnl = 120000 − 85000 = 35000
    remainder = { quantity 1.5, totalCost 1.5 × 70000 = 105000 }

  LIFO:
    lots = [1 @ 50000, 2 @ 70000]
    consume 1.5 @ 70000
    released  = 1.5 × 70000 = 105000
    proceeds  = 120000; realizedPnl = 120000 − 105000 = 15000
    remainder = { quantity 1.5, totalCost 50000 + 0.5 × 70000 = 85000 }

  These match the M6.2 spec's §9/§10 worked examples exactly.

Concerns / design decisions
===========================

  - The AVERAGE worked example involves a non-terminating average
    (190000 / 3), so in code the released basis is truncated to
    94999.999999999999999999999999995 and the remainder cost to
    95000.000000000000000000000000005 (26 fractional digits, §11); the values
    shown above are the ideal ones, which the code approaches to < 10^-26.
    The FIFO/LIFO examples are exact. The cross-strategy test in the engine
    suite uses a terminating ledger (buy 1@100, buy 1@200, sell 1.5@160) so
    the assertions are exact.
  - The M6.2 report supersedes the "SELL keeps totalCost" note in the M6.1
    report's sections 9 and 20; SELL now releases basis under all three
    policies.
