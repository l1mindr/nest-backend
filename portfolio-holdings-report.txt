PORTFOLIO HOLDINGS REPORT — MILESTONE M2
==========================================

1. ARCHITECTURE
===============

The Portfolio feature (src/features/portfolio/) follows the project's layered
architecture with domain-driven entity modeling:

  portfolio/
  ├── application/         # Use cases, interfaces, mappers
  │   ├── interfaces/      # Repository + use-case contracts (Symbols + interfaces)
  │   ├── mappers/         # Entity → DTO mapping
  │   └── use-cases/       # 7 use cases: CRUD for portfolios and holdings
  ├── domain/              # Entities, errors (framework-agnostic)
  │   ├── entities/        # Portfolio + Holding (TypeORM)
  │   ├── enums/           # PortfolioSourceType
  │   └── errors/          # PortfolioErrors + PortfolioErrorCode
  ├── infrastructure/      # TypeORM repositories, DB constraint handler
  │   ├── providers/       # Unique constraint violation handler (23505 mapping)
  │   └── repositories/    # Portfolio + Holding repositories
  ├── presentation/        # Controllers, DTOs, Swagger, validators
  │   ├── controllers/     # PortfoliosController + HoldingsController
  │   ├── dto/             # Request + response DTOs
  │   ├── swagger/         # API documentation decorators
  │   └── validators/      # DecimalString custom validator (for amounts)
  └── portfolio.module.ts  # NestJS module wiring

Domain models:
- Portfolio: represents a user's data source (Ledger, Exchange, Personal Wallet,
  Other). Scoped to the authenticated user. No cross-user access.
- Holding: represents the amount of an Asset held in a specific Portfolio.
  References Asset by UUID — never duplicates asset metadata.

Money strategy: amounts stored as PostgreSQL numeric(36,18), typed as string in
TypeORM entities and DTOs. No JavaScript floating-point arithmetic.


2. DOMAIN MODEL
===============

Portfolio entity (table "portfolio"):
  id             uuid (PK, auto-gen)
  userId         uuid (FK → user, indexed)
  name           varchar(100)
  sourceType     enum (LEDGER, EXCHANGE, WALLET, OTHER)
  walletAddress  varchar(255) nullable
  createdAt      timestamptz
  updatedAt      timestamptz

Holding entity (table "holding"):
  id           uuid (PK, auto-gen)
  userId       uuid (FK → user, indexed)
  portfolioId  uuid (FK → portfolio, indexed)
  assetId      uuid (FK → asset, indexed)
  amount       numeric(36,18) — decimal string
  notes        varchar(1000) nullable
  createdAt    timestamptz
  updatedAt    timestamptz

Constraints:
  uq_holding_portfolio_asset — UNIQUE (portfolioId, assetId)
  Enforces: one holding per (portfolio, asset) pair per user.

Relations: User, Portfolio, Asset — all FK with ON DELETE NO ACTION.

4. API ENDPOINTS
================

Portfolios:
  POST   /v1/portfolios         — create portfolio source (CSRF)
  GET    /v1/portfolios         — list user's portfolio sources
  GET    /v1/portfolios/:id     — get one portfolio source by UUID

Holdings:
  POST   /v1/holdings           — add holding (CSRF)
  GET    /v1/holdings           — list holdings (optional ?portfolioId filter)
  PATCH  /v1/holdings/:id       — update holding amount/notes (CSRF)
  DELETE /v1/holdings/:id       — remove holding (CSRF)

All mutations: authenticated + CSRF (global guards).
Reads: authenticated only (JwtGuard is APP_GUARD).


5. AUTHORIZATION MODEL
=======================

- Authentication required for all endpoints (JwtGuard APP_GUARD)
- No role restrictions — any authenticated USER/ADMIN/OWNER can manage portfolios
- All queries scoped by userId derived from authenticated request context
- Cross-user access returns 404 (indistinguishable from non-existence — IDOR prevention)
- No @RequirePermissions or @Roles decorators needed
- CsrfGuard handles CSRF tokens globally for state-changing methods

Ownership enforcement:
  PortfolioRepository: findByIdAndUser(id, userId), findByUserId(userId)
  HoldingRepository: findByIdAndUser(id, userId), listByUser(userId, ...), delete(id, userId), update(id, userId, data)
  CreateHoldingUseCase: verifies portfolio belongs to caller before creating
  ListHoldingsUseCase: if portfolioId filter provided, verifies portfolio belongs to caller

Never trusts user-provided userId. Always derived from @User() decorator.


6. OWNERSHIP ENFORCEMENT
=========================

Cross-user attack prevention (verified in E2E):
  - User B cannot create holding in User A's portfolio → 404 PORTFOLIO_NOT_FOUND
  - User B cannot update User A's holding → 404 HOLDING_NOT_FOUND
  - User B cannot delete User A's holding → 404 HOLDING_NOT_FOUND
  - User B cannot list holdings filtered by User A's portfolio → 404 PORTFOLIO_NOT_FOUND
  - User B cannot get User A's portfolio → 404 PORTFOLIO_NOT_FOUND
  - User B cannot see User A's portfolio in their list → filtered by userId

All methods use compound queries: { id, userId } or { where: { userId } }


7. APPLICATION USE CASES
=========================

CreatePortfolio: userId + DTO → validates via class-validator → repository.create

ListPortfolios: userId → repository.findByUserId(userId) → order by createdAt DESC

GetPortfolio: userId + portfolioId → repository.findByIdAndUser → PORTFOLIO_NOT_FOUND

CreateHolding: userId + DTO (portfolioId, assetId, amount, notes?)
  1. Verify portfolio belongs to user (PORTFOLIO_NOT_FOUND)
  2. Verify asset exists (AssetErrors.assetNotFound via ASSET_REPOSITORY)
  3. Create holding via repository (DB unique constraint catches duplicates)
  4. On 23505 → throwOnHoldingUniqueConstraint → HOLDING_ALREADY_EXISTS

ListHoldings: userId + { portfolioId? }
  If portfolioId provided: verify portfolio belongs to user first
  → repository.listByUser(userId, { portfolioId })
  Returns with joined Asset relation

UpdateHolding: holdingId + userId + DTO
  Empty update check → HOLDING_EMPTY_UPDATE
  Repository.update(id, userId, data) → returns updated or null → HOLDING_NOT_FOUND

DeleteHolding: holdingId + userId
  Repository.delete(id, userId) → bool → HOLDING_NOT_FOUND if false


8. VALIDATION
=============

CreatePortfolioRequestDto:
  name: required, trimmed, non-empty, max 100 chars
  sourceType: required, IsEnum(PortfolioSourceType)
  walletAddress: optional, trimmed, max 255 chars

CreateHoldingRequestDto:
  portfolioId: required UUID
  assetId: required UUID
  amount: required decimal string (custom DecimalStringValidator: positive, ≤18 fractional digits, not zero)
  notes: optional, trimmed, max 1000 chars

UpdateHoldingRequestDto:
  amount?: optional decimal string
  notes?: optional trimmed max 1000

DecimalStringValidator (presentation/validators/decimal-string.validator.ts):
  Regex: /^\d+(\.\d{1,18})?$/ + zero rejection
  Rejects: non-strings, negative, zero, >18 decimal places, non-numeric

12. REMAINING CONSIDERATIONS
=============================

a) Portfolio value calculation: The current milestone stores raw amounts and
   references assets by UUID. Portfolio value (amount × currentPrice) is NOT
   computed here — it would require joining asset prices and computing in the
   API layer or a service. This is a natural next step.

b) Portfolio update endpoint: Not implemented (spec only required create + list).
   A PATCH /v1/portfolios/:id for renaming or changing sourceType can be added
   with the same ownership-scoping pattern.

c) Portfolio delete endpoint: Not implemented. ON DELETE NO ACTION prevents
   accidental cascade. If portfolio deletion is needed later, cascade behavior
   (soft-delete or holding removal) should be explicitly designed.

d) Holding amount precision: numeric(36,18) handles tokens with up to 18
   decimal places (Ethereum standard). Tokens with >18 decimals would need
   a migration to increase precision.

e) No transaction isolation concerns: each holding create/update/delete is a
   single row operation with ownership check. No multi-table invariants.

f) No rate limiting applied to portfolio endpoints — the global security
   framework (JwtGuard, CsrfGuard) provides baseline protection. Dedicated
   rate limits can be added per the RateLimitPolicies pattern if needed.

g) No Redis caching — reads are direct DB queries. The user's portfolio
   data is bounded in size and does not require caching at this scale.
