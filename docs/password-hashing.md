# Password Hashing

This document describes how passwords are hashed, why, and how the bcrypt →
Argon2id migration works. It is the single source of truth for the password
storage architecture.

## Why Argon2id

Passwords were previously hashed with bcrypt at cost 10. bcrypt is a correct
choice but Argon2id is the current recommended algorithm:

- **Winner of the Password Hashing Competition (2015)** and the OWASP-recommended
  algorithm for new password storage.
- **Hybrid mode** — Argon2id runs Argon2i (memory-hard, data-independent) for the
  first half and Argon2d (data-dependent) for the second. It resists both
  **side-channel attacks** (which exploit data-dependent memory access, the
  weakness of Argon2d) and **GPU/ASIC cracking** (which Argon2i is weaker
  against). Neither pure Argon2i nor pure Argon2d is acceptable for password
  hashing; only Argon2id is used by this system.
- **Tunable memory, time, and parallelism** gives a better resistance-per-CPU
  ratio than bcrypt, whose only lever is the cost factor.

## Parameters

Configured via environment variables, validated at startup by the Joi schema in
`src/infrastructure/config/env/env.schema.ts`, and read in one place:
`Argon2Provider` (`src/features/auth/infrastructure/providers/argon2.provider.ts`).

| Variable | Default | Bound | Notes |
|----------|---------|-------|-------|
| `ARGON2_MEMORY_COST` | `65536` | 8192 – 1048576 KB | Memory in KB used per hash |
| `ARGON2_TIME_COST` | `3` | 1 – 10 | Iterations |
| `ARGON2_PARALLELISM` | `4` | 1 – 16 | Lanes (threads) |
| `ARGON2_HASH_LENGTH` | `32` | 16 – 64 bytes | Output length |

The **salt is 16 bytes**, generated by the library from a CSPRNG on every hash
— the Argon2 reference default; there is no configuration knob for it.

### Rationale for the production configuration (`m=65536, t=3, p=4, l=32`)

- **Memory 64 MiB.** OWASP's floor is 19 MiB at `t=2`. 64 MiB is over three
  times that floor, materially raising the cost of a GPU brute-force attack
  while remaining affordable: a request-scoped hash lives a few hundred
  milliseconds and the container is not memory-constrained (no memory limit in
  `docker/production`).
- **Time cost 3.** OWASP's recommendation is 2 iterations; 3 is a margin on
  top without an appreciable latency hit.
- **Parallelism 4.** One lane per typical vCPU. Argon2's `m` is split across
  lanes, so each lane uses 16 MiB here.
- **Hash length 32.** A 256-bit output — beyond any practical brute-force
  horizon.
- **Salt 16 bytes.** The RFC 9106 reference value.

These parameters intentionally make hashing expensive (that is the point of a
password hash). The goal is not speed; the bounds in the schema exist to stop a
misconfiguration from silently weakening storage, and the login/registration
paths are rate-limited.

## Architecture

```
HashingProvider (abstract, application-facing contract)
  └─ Argon2Provider (concrete, infrastructure)
       ├─ Argon2id hash    → all new passwords
       ├─ Argon2id verify  → $argon2id$... hashes
       ├─ bcrypt verify    → $2a/$2b/$2x/$2y$... legacy hashes
       └─ reject           → anything else
```

- **Application code depends on the abstraction only.** Use cases inject
  `HashingProvider` and never see a hash format. `needsMigration(hash)` on the
  abstraction lets the login flow ask "is this legacy?" without knowing
  anything about prefixes.
- **Concrete implementation is infrastructure.** The only Argon2/bcrypt calls
  in the system live in `Argon2Provider` (and the verification-code service,
  which is out of scope here).
- **One configuration source.** Parameters come from env, validated in
  `env.schema.ts`, read only in `Argon2Provider`.

## Flows that create Argon2id hashes

Every password creation path goes through `HashingProvider.hash`, so every one
of these produces Argon2id once the provider is wired in:

- Registration (`Register` → `InitiateRegistrationUseCase`)
- Password change (`ChangePassword`)
- Administrator invitations (`AcceptAdminInvitationUseCase`)

There is no separate implementation for `USER`, `ADMIN`, or `OWNER` accounts —
the same `HashingProvider` boundary is used everywhere. No new bcrypt hashes are
created after the migration.

## Legacy bcrypt support and automatic migration

Existing accounts keep working without a password reset.

The stored hash carries its own algorithm identifier, so no database column is
needed to choose a verifier:

- `$argon2id$...` → verify with Argon2id
- `$2a$` / `$2b$` / `$2x$` / `$2y$` → verify with bcrypt
- anything else → rejected as unsupported (no weak verification fallback)

On a **successful bcrypt login** the login use case:

1. verifies the password with bcrypt (in `Argon2Provider.compare`),
2. authenticates the user normally,
3. rehashes the plaintext with Argon2id **in the background**,
4. stores the Argon2id hash with a **conditional update**:

```sql
UPDATE users
SET password = :newHash
WHERE id = :userId AND password = :currentBcryptHash
```

The `WHERE password = :currentBcryptHash` guard is what makes concurrent logins
safe: if another request already migrated the hash, or the user changed their
password, the update affects zero rows and the newer hash is left untouched.

### Migration failure

The migration runs off the request path. If hashing or the update fails, the
login **still succeeds** (the password was already verified), a structured
`auth.password.migration_failed` event is logged, the bcrypt hash is retained,
and the migration is retried on the next successful login. No hashing error is
ever shown to the user.

### Plaintext hygiene

The plaintext password exists only in memory for the duration of
authentication and rehash. It is never returned to the client, never logged
(the migration events log only `userId`), and never placed in a job or stored
anywhere else.

## When bcrypt can be removed

bcrypt (`bcrypt` dependency, the legacy branch in `Argon2Provider`, and the
verification-code hashing) must stay as long as legacy hashes can exist in the
database. The dependency is removed only after all of:

1. No new bcrypt hashes are created (true since this migration: every write
   path produces Argon2id).
2. Every authentication path supports migration (login and change-password
   both write Argon2id).
3. No bcrypt hashes remain in production. Migration is lazy — bcrypt disappears
   from the database as users log in. A SQL audit such as
   `SELECT count(*) FROM "user" WHERE "password" LIKE '\$2%';` returning zero
   over a sustained window (longer than the longest-absent-user horizon) is the
   signal.

This project has not shipped with real users yet, so a **clean migration** is
safe: the deploy that enables Argon2id can simply drop bcrypt verification once
no bcrypt rows exist. If real bcrypt rows ever exist in production, the lazy
migration above is the path.

**Verification codes are a separate concern.** `UserVerificationCode` still
hashes 6-digit codes with bcrypt (3-minute TTL); this document does not change
that.

## Performance

Measured locally (`Apple Silicon`, Node v24, native `argon2` binding,
2026-08-08):

| Config | hash p50 | verify p50 |
|--------|----------|------------|
| production (`m=65536, t=3, p=4`) | 22.9 ms | 22.3 ms |
| OWASP minimum (`m=19456, t=2, p=1`) | 14.2 ms | 13.8 ms |
| test env (`m=8192, t=1, p=1`) | 2.6 ms | 2.6 ms |
| bcrypt cost 10 (legacy baseline) | 47.2 ms | — |

16 concurrent production-config hashes completed in 138.6 ms total (8.7 ms
average per op) on this machine.

Numbers vary by hardware; re-run `pnpm exec ts-node scripts/benchmark-argon2.ts`
on the target deployment to verify. Key points:

- Hashing is deliberately expensive; latency is *not* tuned down by weakening
  parameters.
- Each concurrent production hash allocates 64 MiB temporarily. With the
  default libuv threadpool this is bounded, and login is rate-limited, so it is
  affordable for this deployment. Containers with a tight memory limit should
  drop `ARGON2_MEMORY_COST` before touching `ARGON2_TIME_COST`.
