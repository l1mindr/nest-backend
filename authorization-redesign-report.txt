1. OVERVIEW OF THE NEW AUTHORIZATION ARCHITECTURE
--------------------------------------------------------------------------------

The system no longer asks "what role is this caller?" It asks "does this caller
hold the permission this route needs?" Roles remain, but only to express three
tiers, and only one of them — the owner — short-circuits the question.

A new feature module, `src/features/authorization/`, owns the model. It follows
the layer layout every other feature uses (domain / application / infrastructure
/ presentation) rather than inventing a shape of its own.

  Request path
  ------------
    JwtGuard          authenticates, attaches req.user { id, role }
        ↓
    RateLimitGuard
        ↓
    RolesGuard        only for routes reserved to a tier outright (@Roles)
        ↓
    PermissionGuard   reads @RequirePermissions, asks the evaluation service
        ↓
    CsrfGuard
        ↓
    Controller → Use case

  Decision path (PermissionEvaluationService)
  -------------------------------------------
    owner?  ──────────────────────────────► allow, with no database lookup
       │ no
       ▼
    load the grants held by this account
       │
       ▼
    holds every required permission?  ──► allow / deny (403 ACCESS_DENIED)

Four properties are worth calling out, because they are what make the design
survive future change:

  * One decision point. `PermissionEvaluationService` is the only component that
    answers a permission question. The guard holds no rule of its own, so a
    decision reached in a guard and one reached inside a use case cannot drift
    apart.

  * No per-role branch. Roles below administrator hold no grants, so they fall
    out of the same evaluation as denied. Nothing has to be restated when a tier
    is added.

  * Owner bypass expressed once. `RoleHierarchy.satisfies` compares by rank, not
    equality, so `@Roles(ADMIN)` is also satisfied by the owner. There is no
    `if (role === OWNER)` anywhere outside `RoleHierarchy`.

  * Resource-level invariants live with the use case. A guard knows which route
    was called but not which record is being acted on. Rules of the form "not
    against the owner", "not against yourself" are therefore preconditions
    asserted by the use case, funnelled through one policy and one shared
    account-resolution service so a new use case cannot forget one.

2. ROLE HIERARCHY
--------------------------------------------------------------------------------

  Role     Rank   Reach
  -----    ----   ---------------------------------------------------------------
  OWNER      30   Exactly one exists. Bypasses every authorization check.
  ADMIN      20   Reaches only what has been granted. The role alone grants
                  nothing at all.
  USER       10   Reaches only its own resources. Behaviour unchanged.

Ranking lives in `src/features/authorization/domain/role-hierarchy.ts`:

    satisfies(role, minimum)        rank(role) >= rank(minimum)
    bypassesAuthorization(role)     role === OWNER — the single owner short-circuit
    isAdministrative(role)          rank(role) >= ADMIN_RANK

The hierarchy is code, not data, deliberately: a tier that could be reordered at
runtime would let a data change grant privilege. Granularity *within* the
administrator tier is data, which is exactly where flexibility is wanted.

USER behaviour is untouched. Ownership is still enforced the way it always was —
by scoping queries to `req.user.id` — and no new abstraction was introduced for
it, because none was needed.

3. PERMISSION MODEL
--------------------------------------------------------------------------------

Single source of truth: the `Permission` enum
(`src/features/authorization/domain/enums/permission.enum.ts`).

`PERMISSION_CATALOG` is typed `Readonly<Record<Permission, string>>`, so adding
an enum member without describing it is a compile error. That is what keeps the
catalog from drifting away from the enum.

  Permission         Grants
  ----------------   ------------------------------------------------------------
  USER_READ          Read any user account and list the directory
  USER_CREATE        Create accounts on behalf of others               (reserved)
  USER_UPDATE        Edit the profile of any user account
  USER_DELETE        Delete any user account                           (reserved)
  USER_SUSPEND       Suspend a user account and revoke its sessions
  USER_UNSUSPEND     Lift a suspension
  ADMIN_READ         Read the administrator directory and the catalog
  ADMIN_UPDATE       Edit another administrator's profile
  ROLE_ASSIGN        Grant and revoke permissions on other administrators
  AUDIT_READ         Read the audit trail                              (reserved)
  SYSTEM_SETTINGS    Change system-wide settings                       (reserved)

"Reserved" means seeded in the catalog and grantable, but no route demands one
yet. They are named in the requested model and cost nothing to carry; the
endpoint that eventually needs one arrives without a second round of migrations
and grants.

  Permission matrix
  -----------------
  GET    /v1/admin/users                        USER_READ
  GET    /v1/admin/users/:id                    USER_READ
  POST   /v1/admin/users/:id/suspend            USER_SUSPEND
  PATCH  /v1/admin/users/:id/unsuspend          USER_UNSUSPEND
  GET    /v1/admin/admins                       ADMIN_READ
  GET    /v1/admin/admins/:id                   ADMIN_READ
  PATCH  /v1/admin/admins/:id                   ADMIN_UPDATE
  POST   /v1/admin/admins/:id/permissions       ROLE_ASSIGN
  DELETE /v1/admin/admins/:id/permissions       ROLE_ASSIGN
  GET    /v1/admin/permissions                  ADMIN_READ
  GET    /v1/admin/permissions/me               authenticated
  POST   /v1/admin/admins                       OWNER only
  DELETE /v1/admin/admins/:id                   OWNER only
  POST   /v1/admin/admins/:id/activate          OWNER only
  POST   /v1/admin/admins/:id/deactivate        OWNER only
  POST   /v1/admin/admins/:id/suspend           OWNER only
  PATCH  /v1/admin/admins/:id/unsuspend         OWNER only

  Administrator archetypes — descriptions of a grant set, not schema types
  -----------------------------------------------------------------------
  Read-only   USER_READ
  Support     USER_READ, USER_UPDATE
  Moderator   USER_READ, USER_SUSPEND
  Super       every permission — still below the owner

Requirements are conjunctive: `@RequirePermissions(A, B)` demands both.

Freshness: grants are read per request and never carried in the access token, so
a revocation lands on the target's very next request rather than at the next
token rotation. The lookup only happens on routes that declare a requirement, so
the ordinary authenticated path pays nothing for it — which matters given the
recent latency work on that path (LAT-004, LAT-009).

4. DATABASE CHANGES
--------------------------------------------------------------------------------

Migration: 1700000005000-CreateAuthorizationTables

  a) user_role_enum rebuilt as ('OWNER', 'ADMIN', 'USER')

     Rebuilt rather than extended with ALTER TYPE ... ADD VALUE, because
     migrations run inside a transaction and PostgreSQL refuses to *use* an enum
     value added in that same transaction — which the single-owner index below
     has to do. Rebuilding keeps the whole migration atomic.

     Existing rows keep their ADMIN or USER role. The column default stays USER.

  b) Partial unique index — the database half of the single-owner invariant

       CREATE UNIQUE INDEX "uq_user_single_owner"
         ON "user" ("role") WHERE "role" = 'OWNER';

     Every row matched by the predicate holds the same value, so uniqueness on
     that value means at most one such row can exist. Two concurrent promotions
     cannot both commit, whatever the application layer believes.

  c) permission — the catalog, reference data seeded by migration

       code         varchar(64)  PK
       description  varchar(255) NOT NULL

     Seeded with the 11 codes above as SQL literals rather than derived from
     PERMISSION_CATALOG: a migration is history and must keep producing the same
     schema however the catalog is edited later.

  d) admin_permission — one row per permission granted to one administrator

       id           uuid PK  default uuid_generate_v4()
       userId       uuid     FK → user(id)        ON DELETE CASCADE
       permission   varchar  FK → permission(code) ON DELETE RESTRICT
       grantedById  uuid     FK → user(id)        ON DELETE SET NULL, nullable
       grantedAt    timestamp default now()
       UNIQUE (userId, permission)
       INDEX (userId)

     The foreign key to the catalog means a grant can only ever name a
     permission the system knows about — a bug or a stray write cannot invent
     privilege from an arbitrary string. `grantedById` is retained so a
     privilege can be traced back to whoever handed it out.

Verified against a real PostgreSQL instance: up, second-owner rejection at the
database level, down (owner demoted to ADMIN before the enum shrinks), and
re-up, all on a scratch database.

Test-infrastructure consequence: `truncateDatabase` now holds back reference
tables, since truncating `permission` would leave every later spec without the
catalog its foreign keys point at.

5. NEW ENDPOINTS
--------------------------------------------------------------------------------

AdminAccountsController — /v1/admin/admins

  GET    /                        ADMIN_READ    List administrators + grants
  GET    /:id                     ADMIN_READ    One administrator + grants
  POST   /                        OWNER         Promote an active account
  DELETE /:id                     OWNER         Withdraw administrator status
  PATCH  /:id                     ADMIN_UPDATE  Edit an administrator's profile
  POST   /:id/activate            OWNER         Restore a deactivated admin
  POST   /:id/deactivate          OWNER         Switch off access, end sessions
  POST   /:id/suspend             OWNER         Suspend (reuses the shared flow)
  PATCH  /:id/unsuspend           OWNER         Lift the suspension
  POST   /:id/permissions         ROLE_ASSIGN   Grant permissions (idempotent)
  DELETE /:id/permissions         ROLE_ASSIGN   Revoke permissions (idempotent)

PermissionsController — /v1/admin/permissions

  GET    /                        ADMIN_READ    The permission catalog
  GET    /:me                     authenticated What the caller can do right now

Two design decisions here deviate from a literal reading of the brief. Both are
deliberate, and both are narrower rather than wider than what was asked:

  * "Create admin" promotes an existing active account instead of registering a
    new one. An administrator is an ordinary account holding a role, not a
    separate identity, so registration, email verification and password handling
    stay on the single path they already follow. A create-a-user-with-credentials
    endpoint would duplicate that path and, worse, would let one account mint
    credentials for another — a straightforward account-takeover primitive. The
    brief also required that existing authentication remain unchanged, which
    this respects.

  * "Delete admin" withdraws the role rather than destroying the account: role
    set to USER, all grants deleted, all sessions revoked, in one transaction.
    Removing administrative reach and deleting a person's data are separate
    decisions; merging them would mean the owner could not demote a colleague
    without destroying their account. Account deletion stays where it already
    lives, on `DELETE /v1/user/delete-account`.

`GET /v1/admin/permissions/me` was not requested. It is included because a
client that renders navigation from the same answer the server enforces cannot
drift out of step with it, and because the alternative — clients inferring reach
from the role — is exactly the coupling this redesign removes.

6. SECURITY IMPROVEMENTS
--------------------------------------------------------------------------------

  Vertical escalation
    * ROLE_ASSIGN alone is not equivalent to every permission. A caller can only
      delegate permissions they themselves hold (`assertCanDelegate`). Without
      that limit, an administrator could grant the rest to a colleague and have
      them grant those back.
    * The same limit applies to revocation, so a narrowly-scoped administrator
      cannot disarm a colleague whose reach exceeds their own.
    * Self-targeting is refused across every administrative operation by a
      single rule (`assertNotSelf`), covering self-promotion, self-granting and
      self-demotion at once rather than one call site at a time.
    * The administrator lifecycle is owner-only by role, so no permission set
      unlocks minting administrators.

  Owner integrity
    * Exactly one owner, enforced both by the application and by a partial
      unique index — the database constraint holds even under a race the
      application layer loses.
    * OWNER is unreachable through the API: no endpoint accepts a role, and
      `assertRoleAssignable` stands in front of the one place a role is written.
    * The owner cannot be suspended, unsuspended, demoted, deactivated, edited
      by another account, or deleted — refused even on their own account, since
      no endpoint could appoint a replacement.
    * The owner remains an ordinary account to themselves: password change,
      profile update and email verification are unaffected.

  Horizontal escalation
    * Unchanged and still correct: user-facing reads and writes are scoped to
      `req.user.id`, so one user cannot address another's resources.

  Token / session freshness
    * Grants are never carried in the access token, so revocation is immediate.
    * Demotion and deactivation revoke all sessions, because a token issued
      earlier carries the role the account no longer holds.

  Information disclosure
    * `403 ACCESS_DENIED` carries no metadata. Which permission was missing
      belongs in the logs, not in a response an attacker can read. The
      authorization-specific errors that *do* explain themselves
      (OWNER_IMMUTABLE, PERMISSION_NOT_HELD, …) only fire after the caller has
      already passed the permission gate.

  Data integrity
    * A grant can only name a permission in the catalog (foreign key), and DTO
      validation rejects unknown codes before that.
    * Grants are unique per (administrator, permission) and idempotent, so a
      replayed request is never an error and never duplicates state.

  Auditability
    * `grantedById` records who handed out each privilege.
    * Six new log events: admin role granted/revoked, status changed, profile
      updated, permissions granted/revoked.

7. BREAKING CHANGES
--------------------------------------------------------------------------------

One behavioural change, and it is the point of the redesign:

  * An account holding ADMIN no longer reaches `/v1/admin/*` by virtue of the
    role. It reaches exactly what has been granted to it. Existing ADMIN
    accounts therefore have no access until permissions are granted, or until
    one account is promoted to OWNER.

    Migration path for an existing deployment:
      1. Promote one verified, active account to OWNER (see §12).
      2. As that owner, grant each existing administrator the permissions they
         actually need — `GET /v1/admin/permissions` lists the options.

No API contract was broken:

  * No route was removed, renamed or re-shaped.
  * No response body changed. `role` still serializes as a string and still
    appears in the same DTOs; `OWNER` is simply a new possible value.
  * Status codes are unchanged — an insufficiently privileged caller still
    receives `403 ACCESS_DENIED`, exactly as before.
  * Authentication is untouched: same cookies, same tokens, same flows.
  * USER behaviour is untouched end to end.

Internal (non-API) changes a maintainer should know about:

  * `IUserRepository` gains `findUsersByRole` and `updateRole`.
  * `findUserById` now selects `role` alongside `id`, so the callers using it as
    an existence check can refuse to act on the owner without a second query.
  * `UsersModule` additionally exports the suspend and unsuspend use cases.
  * `truncateDatabase` (test helper) holds back reference tables.

8. FUTURE EXTENSIBILITY ANALYSIS
--------------------------------------------------------------------------------

  Add a permission to an administrator          data only — one API call
  Remove a permission                           data only — one API call, takes
                                                effect on the next request
  Introduce a new permission                    enum member + catalog description
                                                + seed migration. The route that
                                                requires it is code either way,
                                                so this is the floor, not
                                                overhead.
  Protect an existing route                     one decorator, no other change
  Add a new administrative route                declare @RequirePermissions; the
                                                guard and service are already
                                                wired globally

  Named custom admin roles (e.g. SUPPORT_ADMIN bundling permissions)
    An `admin_role` / `admin_role_permission` pair plus one extra branch in
    `PermissionEvaluationService` to union role-derived grants with per-account
    ones. Controllers, guards, decorators, DTOs and use cases are unaffected,
    because they speak in permissions rather than roles. This is the specific
    "evolve without another redesign" requirement, and the seam is the
    evaluation service.

  A fourth tier
    Add the enum value, give it a rank, and grant it permissions. No call site
    changes: `RolesGuard` compares by rank and `PermissionGuard` does not know
    roles exist beyond the owner short-circuit.

  Resource-scoped permissions (e.g. "moderate only region X")
    Not supported, and deliberately not designed for. The honest extension point
    is a scope column on `admin_permission` plus a predicate in the evaluation
    service. Flagged rather than built, since nothing in the brief needs it and
    speculative generality here would cost clarity now.

  Caching
    Currently one indexed lookup per permission-gated request. If that ever
    shows up in a profile, the cache belongs behind
    `IAdminPermissionRepository.findByUserId` with invalidation on grant,
    revoke and demotion — a single seam. Not done now: the query is on the
    administrative path only, and immediate revocation is worth more than a
    micro-optimisation nobody has measured.

12. REMAINING RECOMMENDATIONS AND FUTURE IMPROVEMENTS
--------------------------------------------------------------------------------

  REQUIRED BEFORE DEPLOY

  1. Appoint the owner. No migration creates one, deliberately: it would need
     credentials, and a seeded row with a placeholder password is a
     default-credential liability. Promote a real, verified account:

         UPDATE "user" SET role = 'OWNER'
         WHERE email = 'owner@example.com' AND status = 'ACTIVATE';

     The unique index guarantees this can only succeed once. Consider wrapping
     it in a `scripts/promote-owner.ts` CLI alongside the existing
     `generate-secrets.ts` if this is done often enough to be worth automating.

  2. Grant existing administrators their permissions. Until then they hold the
     role and reach nothing — see §7.

  RECOMMENDED NEXT

  3. Audit trail. `AUDIT_READ` is seeded but no audit log exists. The six new
     log events carry the right shape (actor, target, permissions) to be
     persisted rather than only written to the log stream.

  4. Consider whether `USER_CREATE`, `USER_DELETE` and `SYSTEM_SETTINGS` should
     acquire endpoints or be dropped from the catalog. They are named in the
     model but nothing demands them; a permission an operator can grant that
     changes nothing is a small trap.

  5. The pre-existing claim in the admin-users OpenAPI description that the
     listing includes soft-deleted accounts does not match `findUsersForAdmin`,
     which excludes them via the soft-delete column. Untouched here because it
     predates this work and is not an authorization concern, but worth a
     separate fix.

  6. Domain-layer isolation remains disabled in ESLint because entities still
     carry TypeORM decorators and errors import `HttpStatus`. The new
     authorization domain follows the same existing pattern rather than
     diverging from it; it would move cleanly if that debt is ever paid.

  OPTIONAL

  7. Named custom admin roles, when the archetypes stop being ad-hoc grant sets
     and start needing names. Design and seam described in §8.

  8. Reordering `CsrfGuard` ahead of `PermissionGuard` would spare a database
     lookup on forged requests. Left alone because it changes existing guard
     ordering and existing behaviour for a marginal gain.

PHASE 2 — INVITATION FLOW, OWNER-ONLY ADMINISTRATION, ISOLATION, OWNER VISIBILITY
================================================================================

Phase 1 delivered permission-driven access control. Phase 2 replaces the last
role-based decision with a permission that only the owner can ever hold, swaps
promotion for an invitation flow, and seals the boundary between the user and
administrator populations. Everything here is a Phase-2 change; the Phase-1
verification below this section remains the record for what it shipped.


-------------------------------------------------------------------------------
2.1 OWNER-ONLY ADMINISTRATION WITHOUT A ROLE CHECK
-------------------------------------------------------------------------------

Phase 1 reserved the administrator lifecycle to the owner with @Roles(OWNER) on
the controller — a decision enforced by role at the call site. Phase 2 removes
that mechanism entirely.

PERMISSION_CATALOG entries now carry an ownerOnly flag:

    interface PermissionMeta {
      description: string;
      ownerOnly:   boolean;   // can never be granted, never satisfies anyone
    }                          // but the owner, who bypasses evaluation anyway

    ADMIN_READ, ADMIN_INVITE, ADMIN_UPDATE, ADMIN_DELETE,
    ADMIN_STATUS, ROLE_ASSIGN        →  ownerOnly: true
    USER_*, AUDIT_READ, SYSTEM_SETTINGS →  ownerOnly: false

Every administrator route still declares @RequirePermissions(...) exactly like
a user-facing route. There is no @Roles anywhere in the authorization
controllers. The owner-only rule lives in the catalog, not in a controller,
because:

  * the guard refuses on the ordinary permission path — the only mechanism it
    knows — so there is no second, role-shaped decision to drift from it;
  * no grant row can name an owner-only code (DTO validation rejects them with
    422 before a use case runs), so no permission set ever unlocks them;
  * relaxing the restriction later is one flag per permission, and granting it
    to an administrator. No controller, guard or use case changes.

DELEGABLE_PERMISSIONS derives from the flag: (Object.keys(PERMISSION_CATALOG))
.filter(p => !ownerOnly). PermissionSetRequestDto validates @IsIn(...) against
it, so an owner-reserved code in a grant, revoke or invitation payload is a
validation error, not a runtime surprise.


-------------------------------------------------------------------------------
2.2 ADMINISTRATOR INVITATIONS REPLACE PROMOTION
-------------------------------------------------------------------------------

Creating an administrator no longer promotes an existing account. It issues an
invitation; the account is created only when the invitee accepts it.

    owner                            server                           invitee
      │ POST /administrators/invitations                              │
      │ { email, permissions }                                        │
      │  ──────────────────────────────────►                          │
      │    201 { id, email, expiresAt } (never the token)             │
      │                                                                │
      │                       email  [ accept-link?token=... ]        │
      │  ◄────────────────────────────────────────────────────────────│
      │                                                                │
      │                       POST /administrators/invitations/accept │
      │                        { token, username, password, name }    │
      │  ◄────────────────────────────────────────────────────────────│
      │                       204 (account created, ADMIN, ACTIVATE)  │

  * Until acceptance, NO ACCOUNT EXISTS. A revoked or lapsed invitation leaves
    nothing that could be signed into — the property that made promotion
    untenable, since promotion creates the privileged account up front and a
    forgotten invite leaves a dormant administrator behind.
  * The token is 32 bytes from a CSPRNG, sent only by email, and stored only as
    a SHA-256 digest (tokenHash, select: false). A database dump yields nothing
    that could be presented. 256 bits of entropy means the plain digest has no
    dictionary to run against.
  * Single-use, expires after 48 hours, revocable while pending. Re-inviting an
    address supersedes (revokes) any outstanding invitation for it first, so
    lapsed re-invites are one call rather than revoke-then-invite.
  * An address that already has an account cannot be invited (422 EMAIL_ALREADY
    EXISTS), so acceptance can never collide with an existing login.
  * The accepted email comes from the invitation row, never from the body, and
    the accept route is @Public() + @SkipCsrf() — the token is the entire proof
    of entitlement, and the invitee has no account or session yet. A CSRF token
    would add nothing to a 256-bit bearer proof.
  * The only place in the system that writes the ADMIN role is
    AcceptAdminInvitationUseCase, and even there assertRoleAssignable(ADMIN)
    stands in front of the write, so OWNER cannot arrive however it is called.
  * Everything happens in one transaction: create the account, grant the
    invited permissions (as real admin_permission rows with their catalog FK,
    grantedById = the inviter), and burn the invitation. Any failure rolls all
    of it back and the token stays usable.
  * The account is created ACTIVATE with no verification code: receiving the
    token at the invited address already proves control of that mailbox.
  * Unknown, reused and revoked tokens answer 404/409/410 respectively, so the
    endpoint does not confirm whether a given address was ever invited.

"(owner)" marks permissions whose catalog entry forbids delegation. Routes are
reached through the ordinary evaluation; the owner bypasses it, everyone else
fails it with 403 ACCESS_DENIED and no metadata.

DELETE is now a true account deletion rather than a demotion: the account is
hard-deleted and its grants with it. Suspension and unsuspension of an
administrator reuse the shared user flows, told which population they are
administering, so the same use case that cannot touch an administrator through
the user route cannot touch an ordinary user through this one.

2.4 DATABASE CHANGES
-------------------------------------------------------------------------------

Migration: 1700000006000-CreateAdminInvitationTable

  a) permission catalog grows three codes, written as literals:
     ADMIN_INVITE, ADMIN_DELETE, ADMIN_STATUS (ON CONFLICT DO NOTHING).
     Delegability is decided in PERMISSION_CATALOG, not here.

  b) admin_invitation

       id             uuid PK      default uuid_generate_v4()
       email          varchar      indexed (IDX_admin_invitation_email)
       tokenHash      varchar(64)  UNIQUE — sha-256 digest, never the token
       permissions    varchar(64)[] default '{}' — delegable codes only
       expiresAt      timestamp    48 hours after issue
       acceptedAt     timestamp    NULL until settled
       revokedAt      timestamp    NULL until settled
       invitedById    uuid         FK → user(id) ON DELETE SET NULL
       acceptedUserId uuid         FK → user(id) ON DELETE SET NULL
       createdAt      timestamp    default now()

     Status is derived, not stored: PENDING while both timestamps are null,
     ACCEPTED/REVOKED by whichever settled it, EXPIRED when expiresAt passes.

     Partial unique index uq_admin_invitation_pending_email:
       ON (email) WHERE acceptedAt IS NULL AND revokedAt IS NULL
     At most one outstanding invitation per address. Two live tokens for one
     email would both look valid, yet only the first could create the account.

  c) test-infrastructure: migrations.ts registers the new migration; the
     admin_invitation table is cleared between specs by the truncate helper.

Verified against a real PostgreSQL instance: up, duplicate-pending rejection at
the database level, down, re-up.


-------------------------------------------------------------------------------
2.5 ISOLATION AND VISIBILITY
-------------------------------------------------------------------------------

The user and administrator populations are separated at the QUERY level, not
filtered in memory:

  * findUsersByRole(role, cursor, limit) pages one role tier. User management
    pages USER, the administrator directory pages ADMIN. The owner — being
    neither — appears in NO listing at all, including pagination and
    statistics, and cannot be reached through either set of routes.
  * The suspend and unsuspend use cases take a targetRole parameter, so the
    user route can only address USER accounts and the administrator route can
    only address ADMIN accounts.
  * AdminUsersController serves USER only. Administrator identifiers resolve
    to the same 404 USER_NOT_FOUND as identifiers that were never issued, so a
    harvested id cannot be probed.
  * AdminAccountsController serves ADMIN only and is owner-reserved as a whole.
    An administrator cannot list, resolve, edit or suspend a peer. The only
    administrator an administrator can address is themselves, via GET /me —
    which needs no permission because it is scoped to the caller, and which
    exists precisely so a refused directory still has a self-view.
  * The owner's only visibility of itself is through its own account endpoints,
    which behave like any other account's (password, profile, verification).

2.6 SECURITY IMPROVEMENTS — PHASE 2
-------------------------------------------------------------------------------

  Vertical escalation
    * No permission set can unlock administrator management: the ADMIN_* and
      ROLE_ASSIGN codes are owner-reserved in the catalog, cannot be granted,
      and fail validation (422) before a use case runs.
    * The single role write is guarded by assertRoleAssignable, so OWNER can
      never be produced by any code path.

  Horizontal escalation
    * The accept route is public by design, but the token is the entire proof:
      256 bits of CSPRNG entropy, stored only as a digest, single-use, 48h
      expiry, revocable. An unknown token is indistinguishable from one never
      issued (404), so the endpoint is not an oracle for whether an address was
      invited.
    * An address with an existing account cannot be invited, so acceptance
      cannot take over an existing login.

  Information disclosure
    * /admin/users answers 404 identically for an ordinary user id, an
      administrator id, the owner and an unused id. Same for /admin/
      administrators. Enumeration through identifiers is closed at the query
      layer.
    * Invitation acceptance error codes (404/409/410) intentionally do not
      confirm whether an email was ever invited.

  Data integrity
    * Invited permissions are written as real grants inside the acceptance
      transaction, with a catalog foreign key and grantedById, so nothing
      outlives a failed acceptance.
    * At most one pending invitation per address (partial unique index), and
      the token hash is unique, so a token cannot be replayed.

  Auditability
    * New log events: ADMIN_INVITED, ADMIN_INVITATION_ACCEPTED,
      ADMIN_INVITATION_REJECTED (with reason and status), EMAIL_SEND_FAILED.
    * invitedById is retained even after the inviter's account is deleted, and
      recorded at acceptance onto the grants handed out.

  Owner integrity
    * Unchanged from Phase 1 and still enforced: single-owner index,
      assertRoleAssignable, assertNotSelf on every administrator route,
      assertNotOwner on every owner-affecting operation.


-------------------------------------------------------------------------------
2.7 BREAKING CHANGES — PHASE 2
-------------------------------------------------------------------------------

  API contract:
    * /v1/admin/admins is RENAMED to /v1/admin/administrators. Clients must
      update the prefix.
    * POST /v1/admin/admins (promote) is REMOVED, replaced by the invitation
      endpoints.
    * DELETE /v1/admin/administrators/:id now deletes the account instead of
      demoting it to USER. Clients that depended on demotion must re-point to
      an explicit demotion flow if one is added later.
    * /v1/admin/users no longer returns administrators or the owner, because
      they are no longer in the USER population the route serves. Clients that
      expected a complete account directory must read both directories (neither
      of which an administrator can see, by design).
    * Owner-reserved permissions in a grant/revoke/invite payload now fail with
      422 instead of succeeding and being ignored.

  Internal:
    * PERMISSION_CATALOG is no longer Record<Permission, string>; it is
      Record<Permission, PermissionMeta> (description + ownerOnly).
    * IUserRepository gains findUsersByRole; findUserForAdmin/findUsersByRole
      scope by role; suspend/unsuspend take a targetRole argument.
    * GrantAdminRole/RevokeAdminRole use cases are deleted (their DTO,
      create-admin.request.dto.ts, with them); the role is written only by
      invitation acceptance.
    * UsersModule/AuthModule wiring changes for the invitation flow, and the
      email service gains sendAdminInvitationEmail.

2.11 REMAINING RECOMMENDATIONS — PHASE 2
-------------------------------------------------------------------------------

  1. Deliver the invitation email. The token is logged only in the success log
     of the email call, never persisted; the SMTP integration behind
     sendAdminInvitationEmail is the remaining piece to wire in production
     (the e2e suite asserts the helper call, not delivery).

  2. The accept route logs invitation id, status and reason on rejection. The
     endpoint deliberately returns the same code for "unknown token" and
     "never issued", so rate limiting on /invitations/accept is the only
     protection against token guessing — the 256-bit space makes it academic,
     but a per-IP limiter is cheap to add.

  3. Phase-1 recommendation #4 stands: USER_CREATE, USER_DELETE and
     SYSTEM_SETTINGS are still catalog-only. With the invitation flow in place,
     consider whether USER_CREATE should gain an endpoint or be dropped.
