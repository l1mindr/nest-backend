ASSET MANAGEMENT REPORT — MILESTONE M1
=======================================

1. ASSET ARCHITECTURE
=====================

The Asset domain is a standalone feature module (src/features/assets/) following
the project's layered architecture:

  assets/
  ├── application/        # Use cases, interfaces, mappers
  │   ├── interfaces/     # Port + repository + use-case contracts
  │   ├── mappers/        # Entity → DTO mapping
  │   └── use-cases/      # SyncAssets, GetAsset, ListAssets
  ├── domain/             # Entities, errors (framework-agnostic)
  │   ├── entities/       # Asset TypeORM entity
  │   └── errors/         # Domain error factories
  ├── infrastructure/     # Adapters (CoinGecko, BullMQ, TypeORM)
  │   ├── coingecko/      # CoinGeckoPort adapter + config
  │   ├── queues/         # BullMQ processor + scheduler
  │   └── repositories/   # TypeORM repository
  ├── presentation/       # Controllers, DTOs, Swagger
  │   ├── controllers/    # AssetsController (read) + AssetSyncController (sync)
  │   ├── dto/            # Request/response DTOs
  │   └── swagger/        # API documentation decorators
  └── assets.module.ts    # NestJS module wiring

Design principle: Assets are NOT managed by administrators. The external source
of truth is CoinGecko. A background sync process upserts market data into
PostgreSQL. Users browse assets via read-only endpoints.


2. COINGECKO INTEGRATION
=========================

Port/Adapter pattern:

  CoinGeckoPort (application/interfaces/assets.interface.ts)
       ↓
  CoinGeckoAdapter (infrastructure/coingecko/coingecko.adapter.ts)
       ↓
  CoinGecko REST API (/coins/markets)

The port interface defines fetchMarketData(): Promise<CoinGeckoMarketData[]>,
returning normalised market data. The adapter handles:

- Paginated fetching via /coins/markets (per_page=250, order=market_cap_desc)
- Configurable max pages (default 5, i.e., top 1250 assets)
- Optional API key via x-cg-demo-api-key header (COINGECKO_API_KEY env var)
- Sequential page requests (no uncontrolled parallelism)
- 30-second HTTP timeout per request

Configuration (coingecko.config.ts):
- baseUrl: https://api.coingecko.com/api/v3
- apiKey: from COINGECKO_API_KEY env (optional)
- pageSize: 250
- maxPages: 5


3. DATABASE SCHEMA
==================

Table: "asset"

  Column                          Type              Nullable
  ─────────────────────────────── ───────────────── ────────
  id                              uuid              NOT NULL (PK, auto-gen)
  coinGeckoId                     varchar(100)      NOT NULL (UNIQUE)
  symbol                          varchar(32)       NOT NULL
  name                            varchar(100)      NOT NULL
  imageUrl                        varchar           NULL
  currentPrice                    numeric(30,8)     NULL
  marketCap                       numeric(30,2)     NULL
  marketCapRank                   integer           NULL
  totalVolume                     numeric(30,2)     NULL
  circulatingSupply               numeric(30,8)     NULL
  totalSupply                     numeric(30,8)     NULL
  maxSupply                       numeric(30,8)     NULL
  priceChange24h                  numeric(30,8)     NULL
  priceChangePercentage24h        numeric(30,4)     NULL
  lastSyncedAt                    timestamptz       NOT NULL
  createdAt                       timestamptz       NOT NULL (default now())
  updatedAt                       timestamptz       NOT NULL (default now())

Constraints:
  PK_asset_id            — primary key
  uq_asset_coin_gecko_id — unique constraint on coinGeckoId

Indexes:
  IDX_asset_coin_gecko_id — coinGeckoId
  IDX_asset_symbol        — symbol (for search)
  IDX_asset_name          — name (for search)

Money strategy: decimal columns are stored as TypeORM `decimal` (maps to
PostgreSQL `numeric`) and typed as `string` in the entity and DTOs. This
preserves full precision — no floating-point rounding. CoinGecko returns
finite numbers; non-finite values are stored as null.

4. SYNC STRATEGY
================

SyncAssetsFromCoinGeckoUseCase (application layer):

1. Calls CoinGeckoPort.fetchMarketData()
2. Normalises the response:
   - Deduplicates by coinGeckoId (Map)
   - Lowercases + trims coinGeckoId and symbol
   - Trims name
   - Validates required fields (id, symbol, name must be non-empty strings)
   - Coerces numeric fields: finite → string, non-finite → null
   - Skips invalid items (does not throw per-item)
3. If no valid assets remain → throws ASSET_SYNC_EMPTY_RESPONSE
4. Calls AssetRepository.upsertMany() (batched, conflictPaths: ['coinGeckoId'])
5. Updates lastSyncedAt on every upsert
6. Returns { receivedCount, synchronizedCount }

Idempotency: CoinGecko IDs are unique in the DB. Running sync multiple times
updates existing records (skipUpdateIfNoValuesChanged) rather than creating
duplicates.

Failure safety: On CoinGecko API errors, the use case logs the failure and
re-throws. Existing asset data is NEVER deleted. A failed sync leaves the
previous data intact for the next cycle.


5. BULLMQ CONFIGURATION
========================

Queue: "asset-sync"
Worker concurrency: 1 (serialised syncs)

Processor: AssetSyncProcessor (WorkerHost)
- Calls SyncAssetsFromCoinGeckoUseCase.execute()
- Logs start, completion (with counts), and failure

Scheduler: AssetSyncScheduler (OnApplicationBootstrap)
- Registers a repeatable job via BullMQ upsertJobScheduler
- Interval: ASSET_SYNC_INTERVAL env var (seconds, default 3600)
- Job ID: 'sync' (deduplication key — only one repeatable job per queue)
- Retry: exponential backoff with configurable attempts
- Skipped in test environment (IS_TEST)

Queue options (from queue.config.ts → assetSync section):
  ASSET_SYNC_INTERVAL          — repeat interval in seconds (default 3600)
  ASSET_SYNC_QUEUE_ATTEMPTS    — retry attempts (default 4)
  ASSET_SYNC_QUEUE_BACKOFF_MS  — initial backoff delay (default 60000ms)
  ASSET_SYNC_QUEUE_KEEP_COMPLETED — completed jobs retained (default 10)
  ASSET_SYNC_QUEUE_KEEP_FAILED    — failed jobs retained (default 50)


6. FAILURE / RETRY STRATEGY
============================

Temporary CoinGecko outage:
- The processor throws, BullMQ retries with exponential backoff
- Existing asset data remains intact in PostgreSQL
- No assets are deleted on failure
- The next scheduled cycle retries automatically

Permanent failures:
- After exhausting attempts, the job is logged and kept for inspection
  (ASSET_SYNC_QUEUE_KEEP_FAILED = 50)

Rate limiting:
- CoinGecko API limits respected via:
  - Sequential page fetching (no parallel requests)
  - Bounded max pages (default 5)
  - 30-second HTTP timeout
  - Hourly sync interval (configurable)

Data integrity:
- Non-finite numeric values stored as null (not corrupted)
- Missing required fields cause the item to be skipped, not the entire sync
- Upsert with skipUpdateIfNoValuesChanged avoids unnecessary writes


7. API ENDPOINTS
================

GET /v1/assets
  Auth:   Any authenticated user (JwtGuard)
  Query:  cursor?, limit? (1-100, default 20), search?
  Returns: { items: AssetResponseDto[], nextCursor: string | null }
  Search: ILIKE on symbol, name, coinGeckoId

GET /v1/assets/:id
  Auth:   Any authenticated user
  Params: id (UUID)
  Returns: AssetResponseDto
  404:    Unknown asset
  422:    Invalid UUID format

POST /v1/assets/sync
  Auth:   Owner only (@Roles(UserRole.OWNER) + CSRF)
  Returns: { receivedCount: number, synchronizedCount: number }
  403:    Non-owner caller
  422:    Missing CSRF token

All response fields are documented via Swagger with @ApiProperty decorators.
Decimal fields are returned as strings to preserve precision.


8. AUTHORIZATION MODEL
======================

Read endpoints (GET /assets, GET /assets/:id):
  - Authentication required (JwtGuard is APP_GUARD)
  - No role restrictions: USER, ADMIN, and OWNER can all read
  - No permission decorators — the guard stack handles authn

Sync endpoint (POST /assets/sync):
  - @Roles(UserRole.OWNER) — only the owner can trigger manual sync
  - CsrfGuard (APP_GUARD) requires x-csrf-token header
  - Regular users and admins receive 403

No ASSET_* permissions were introduced — asset read is authn-only, and sync
is owner-only via the existing role hierarchy. This avoids bloating the
permission catalog with unused codes.

12. REMAINING CONSIDERATIONS
=============================

a) Redis caching: Not introduced for this milestone. Asset reads hit PostgreSQL
   directly. If read latency becomes a concern under high load, a CachePort
   layer can be added later.

b) Rate limiting on manual sync: The POST /assets/sync endpoint is not rate-
   limited because it requires owner authentication and the CoinGecko adapter
   enforces bounded page fetches. A dedicated @RateLimit can be added if
   operational abuse is observed.

c) CoinGecko data freshness: The default 1-hour interval keeps market data
   reasonably current. For sub-hour freshness, reduce ASSET_SYNC_INTERVAL.
   The CoinGecko free tier permits this; pro tiers allow faster updates.

d) Asset deletion policy: Assets are never deleted — only upserted. If a coin
   is delisted from CoinGecko, it remains in the DB with stale market data.
   A future cleanup job could flag assets not updated within a threshold.

e) The existing coin-tracker Coin entity and CoinGecko integration remain
   separate. They serve the price-alert domain (coin metadata + live prices).
   The Asset entity serves the portfolio domain (supported currencies with
   market data). A future consolidation is possible but not in scope.

f) The ASSET_SYNC_MAX_PAGES and page size are hardcoded in coingecko.config.ts
   defaults. Making them env-configurable would be a natural follow-up if the
   sync needs to cover more or fewer assets.
