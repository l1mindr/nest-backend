PORTFOLIO CALCULATION ENGINE REPORT — MILESTONE M6.1
====================================================

1. OBJECTIVE
============

Implement the domain-level foundation of the Portfolio Calculation Engine: a
pure, deterministic, framework-independent calculation boundary that later
milestones build on for realized P&L (M6.2), unrealized P&L (M6.3), cost-basis
strategies, and portfolio analytics.

The engine:
  - operates on normalized plain domain types (not TypeORM entities)
  - performs no I/O, no logging, no database or HTTP calls, holds no state
  - uses exact BigInt-based decimal arithmetic exclusively — no JavaScript
    floating-point arithmetic anywhere
  - is reusable unchanged from the REST API, background jobs, a CLI, or
    scheduled analytics

M6.1 does NOT implement final realized P&L.
M6.1 does NOT implement final unrealized P&L.
M6.1 does NOT expose an HTTP endpoint.
M6.1 does NOT modify holdings.
M6.1 does NOT persist calculation results.

No migrations were created, no tables were touched, no CoinGecko/network calls
were added, and no controllers or Swagger endpoints were introduced.

2. ARCHITECTURE
===============

The calculation engine lives inside the Portfolio domain layer:

  src/features/portfolio/domain/calculation/
  ├── portfolio-calculation.engine.ts     entry point / orchestration
  ├── cost-basis.calculator.ts            strategy abstraction + average cost
  ├── portfolio-calculation.constants.ts  precision constant
  ├── errors/
  │   ├── calculation-error-code.enum.ts
  │   └── calculation-errors.ts
  ├── types/
  │   ├── calculation-input.types.ts
  │   ├── calculation-result.types.ts
  │   └── calculation-transaction.types.ts
  └── __tests__/
      ├── portfolio-calculation.engine.spec.ts
      └── cost-basis.calculator.spec.ts

The engine depends only on `src/core/decimal/decimal.util.ts` and its own
domain types. It imports nothing from @nestjs, TypeORM, infrastructure,
presentation, or other features. The existing architecture rules were
respected (features may depend on core; core stays framework-agnostic).

3. DOMAIN BOUNDARIES
====================

The engine receives normalized data and knows nothing about:
  - TypeORM entities or repositories
  - DTOs or HTTP requests
  - authenticated users or authorization
  - database decimal objects or NestJS decorators

`assetId` is carried as opaque metadata only; portfolio IDs, user IDs and
current market prices are deliberately not part of M6.1 (the application layer
supplies prices when unrealized-P&L is introduced in M6.3). The input
contract is documented in the types so future application layers can map
DB entities to the domain vocabulary without leaking infrastructure into it.

4. INPUT TYPES
==============

  src/features/portfolio/domain/calculation/types/calculation-input.types.ts
  src/features/portfolio/domain/calculation/types/calculation-transaction.types.ts

CalculationTransaction (the normalized ledger entry):
  { id?, type, amount, price?, fee?, occurredAt }
  - type is the 4-member CalculationTransactionType enum:
    BUY | SELL | TRANSFER_IN | TRANSFER_OUT. DEPOSIT/WITHDRAWAL are not part
    of the calculation vocabulary and are rejected at runtime if they arrive.
  - amount: decimal string, strictly positive.
  - price: decimal string, required for BUY/SELL, optional for transfers. For
    transfers it is preserved but never interpreted as acquisition cost.
  - fee: decimal string, non-negative, preserved separately (never merged into
    cost).
  - id: opaque ordering tie-breaker (e.g. the transaction UUID).
  - occurredAt: ISO 8601, used only for chronological ordering — never in a
    monetary calculation.

PortfolioCalculationInput:
  { assetId?, openingQuantity?, openingCost?, transactions }
  - openingQuantity/openingCost default to '0' and let the engine carry basis
    in from a period before the supplied transaction window.
  - transactions do not need to be ordered; the engine sorts internally.
  - currentPrice is deliberately absent until M6.3.

5. OUTPUT TYPES
===============

  src/features/portfolio/domain/calculation/types/calculation-result.types.ts

PortfolioCalculationResult:
  { quantity, totalCost, averageCost }
  - quantity:   exact decimal string, never negative.
  - totalCost:  exact accumulated acquisition cost, decimal string.
  - averageCost: totalCost / quantity; '0' when quantity is 0 (deterministic
    zero instead of null).

All monetary and quantity values are decimal strings. The trio carries enough
information for future currentValue = quantity × currentPrice, and the
strategy abstraction + transaction vocabulary are the seam M6.2 uses for
realized P&L.

6. DECIMAL STRATEGY
===================

All arithmetic reuses src/core/decimal/decimal.util.ts. M6.1 extended it with
three exact, signed-aware functions (existing behavior untouched):

  - isDecimalString(value)   — grammar predicate (accepts a leading minus).
  - compareDecimals(l, r)    — exact ordering, returns -1 | 0 | 1.
  - subtractDecimals(l, r)   — exact difference, may be signed.
  - divideDecimals(l, r, maxFractionDigits) — exact quotient when the result
    is a finite decimal; otherwise truncates the infinite expansion toward
    zero after maxFractionDigits digits (no rounding).

The pre-existing multiplyDecimals and sumDecimals keep their strict
non-negative guard (the existing test that multiplyDecimals('-1', '2') throws
still passes); comparison/subtraction/division are the signed escape hatch
that later signed P&L work will need. No third-party decimal library was
introduced.

7. TRANSACTION SEMANTICS
========================

The engine must understand exactly four types. Anything else — including
DEPOSIT and WITHDRAWAL, which the M5 schema enum contains — fails with
UNSUPPORTED_TRANSACTION_TYPE. Unsupported types are never silently treated as
BUY, SELL, or zero.

8. BUY BEHAVIOR
===============

BUY introduces both quantity and acquisition cost:
  quantity  += amount
  totalCost += amount × price

Example: BUY 1 @ 50000, BUY 1 @ 70000 → quantity 2, totalCost 120000,
averageCost 60000. A price is required; a missing or non-positive price is a
domain error. Fees are validated but not merged into cost.

9. SELL BEHAVIOR
================

SELL is a disposal event. M6.1 reduces quantity only:
  quantity -= amount
  totalCost is NOT touched.

Releasing cost basis on disposal (proportional removal under an average-cost
policy, per-lot matching under FIFO/LIFO) is part of the realized-P&L policy
and is explicitly deferred to M6.2. A SELL exceeding the available quantity is
a deterministic INSUFFICIENT_QUANTITY error — never a negative quantity.
A price is required (the schema requires it for SELL) and preserved for the
future realized-cost calculation.

10. TRANSFER_IN BEHAVIOR
========================

A transfer into the portfolio changes quantity but is not a purchase:
  quantity += amount
  totalCost is NOT changed.

No market price is invented (asset.currentPrice is never used) and a price on
the transfer is preserved but never interpreted as acquisition cost. This
keeps transfers distinct from BUY, which is essential for correct cost basis.

11. TRANSFER_OUT BEHAVIOR
=========================

A transfer out decreases quantity but is not a sale:
  quantity -= amount
  totalCost is NOT changed.

It produces no realized P&L and no cost-basis release. It is checked against
the available quantity like SELL.

12. COST-BASIS STRATEGY
=======================

  src/features/portfolio/domain/calculation/cost-basis.calculator.ts

CostBasisCalculator is a strategy interface:

  calculate(transactions, opening) -> { quantity, totalCost }

AverageCostCalculator is the M6.1 implementation (average-cost foundation).
Future FIFO and LIFO strategies implement the same interface without touching
the transaction vocabulary, the engine, or the repository layer. The engine
defaults to AverageCostCalculator but accepts any CostBasisCalculator,
including test doubles, via its constructor.

13. ERROR / INVARIANT HANDLING
==============================

Domain failures use a plain, HTTP-agnostic CalculationError carrying a
CalculationErrorCode and an optional field name. No HTTP status code lives in
the engine; the application layer maps these to API errors in a later
milestone.

  INVALID_INPUT                      input is not an object / not an array
  INVALID_DECIMAL                    malformed decimal string
  INVALID_DATE                       occurredAt not parseable
  NEGATIVE_QUANTITY                  opening quantity < 0
  NEGATIVE_AMOUNT                    amount <= 0 (incl. zero) / opening cost < 0
  NEGATIVE_PRICE                     price <= 0 when present
  NEGATIVE_FEE                       fee < 0
  MISSING_PRICE                      BUY/SELL without a price
  INSUFFICIENT_QUANTITY              SELL/TRANSFER_OUT exceeds available
  UNSUPPORTED_TRANSACTION_TYPE       anything outside the 4-type vocabulary

Validation order is deterministic: input shape, occurredAt, opening state,
then per-transaction type → amount → price → fee → quantity invariants.
Malformed strings are rejected rather than coerced.

14. ORDERING BEHAVIOR
=====================

The engine never trusts repository ordering. It sorts internally:

  1. occurredAt ascending (ISO 8601, via Date.parse — used only for ordering,
     never for monetary math).
  2. For equal timestamps, id ascending (deterministic tie-breaker).
  3. Exact ties (same time and id) fall back to the stable input order.

The source array is copied first and never mutated. Equal-timestamp behavior
is covered by tests (id tie-breaker and the no-id stable fallback).

15. PRECISION BEHAVIOR
======================

No intermediate value is ever rounded:
  - BUY 0.1 @ 0.2 → totalCost '0.02', never 0.020000000000000004.
  - 0.1 + 0.2 → '0.3'.
  - averageCost is exact whenever the quotient terminates; when it does not,
    the expansion is truncated toward zero at 26 fractional digits
    (CALCULATION_DIVISION_MAX_FRACTION_DIGITS — the domain's maximum monetary
    scale: amount 18 + price 8), an error below 10^-26 and far beyond any
    storage or presentation precision. No presentation rounding policy was
    defined, as required.

20. EXPLICITLY DEFERRED WORK (M6.2 / M6.3)
===========================================

  - M6.2: realized P&L — SELL/TRANSFER_OUT cost-basis release, realized gain/
    loss per disposal, and the final average-cost/FIFO/LIFO policy selection.
    SELL currently reduces quantity only; totalCost stays at cumulative
    acquisition cost until the policy is defined.
  - M6.3: unrealized P&L and current value — the engine input will gain a
    `currentPrice` field (supplied by the application layer), and
    currentValue = quantity × currentPrice will be derived from the existing
    output types.
  - API surface: no GET /v1/portfolios/:portfolioId/pnl or any HTTP mapping
    of CalculationError codes yet.
  - Persistence: calculation results are computed on demand and never stored;
    no cached P&L columns were considered.
  - Presentation rounding policy for averageCost: explicitly not defined.
  - Application-layer wiring: the engine is a plain class; a future milestone
    registers it through Nest DI (e.g. a factory provider) and maps its domain
    inputs/outputs to/from repository data.

Concerns / design decisions
===========================

  - Division is the only place where an exact decimal string may not exist.
    Terminating quotients (the realistic cases) are exact; non-terminating
    ones are truncated at 26 digits with the policy documented in the code and
    in section 15. If the product ever requires a bounded "average cost" with
    fewer digits, that is a presentation decision to be made in M6.2+.
  - SELL keeping totalCost unchanged (section 9) is intentional and
    documented: releasing basis would require either a rounding policy or a
    realized-P&L policy, both deferred. The average-cost result after a SELL
    therefore reflects cumulative acquisition cost until M6.2 defines
    disposal semantics.
  - The decimal utility now has both a non-negative guard (on
    multiply/sum) and signed comparison/subtraction/division. This asymmetry
    is deliberate and mirrors the M4 report's plan to extend the util for
    signed P&L rather than work around it.
